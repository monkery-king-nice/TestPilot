# 从空白到 5 PASS：完整实测操作清单

这份清单用来在**一台刚 clone 下来的电脑**上，把 TestPilot 的主流程完整走一遍：上传项目 → 平台用大白话追问 → 生成候选用例 → 人工确认 → 发请求执行 → 看报告。

clone 下来时 `backend/data/` 是空的（数据库被 git 忽略），所以项目列表天然是空白，不需要额外清库。

## 演示讲的是什么

给 AI 说了一句想要什么功能 → AI 做出一个能跑的项目，但**没说清的地方它自己拍板了** → 把项目包传进 TestPilot → 平台把这些偷偷定的决定翻成大白话问出来 → 人确认是不是自己想要的 → 平台拿确认后的需求生成用例去测 → 报告告诉我们对不对得上。

一句话：**测的不是「文档全不全」，而是「AI 做出来的，是不是我们本来想要的」。**

## 准备：两个终端，全程别关

**终端 1 —— 被测试的小游戏（18085）**，在仓库根目录：

```powershell
python examples/arrow-game/arrow_game_http.py examples/arrow-game/一箭又一箭_测试需求简版.zip --port 18085
```

**终端 2 —— TestPilot 平台（网页 5173 + 后台 8000）**：

```powershell
$env:DEEPSEEK_API_KEY = [System.Net.NetworkCredential]::new('', (Read-Host 'DeepSeek API Key' -AsSecureString)).Password
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/start.ps1 -NoDemo
```

第二次启动可加 `-SkipInstall` 跳过重复安装。三行各管一件事：

- 第一行是 DeepSeek 密钥。不设也能起平台、能上传、能执行，但「需求澄清 / 生成用例 / 失败分析」这些 AI 按钮会提示没 key。**要走完整追问流程必须设。**
- `-NoDemo` 跳过那个多余的假登录演示服务，所以不用设 `DEMO_PASSWORD`。
- **别加 `-NoModel`**，它会把密钥从后台环境里清掉。

前提：Python 3.11+、Node.js 18+、npm 8+（`node -v` 能跑即可），首次启动要联网装依赖；5173、8000、18085 三个端口要空闲。看到 `[READY] frontend: http://127.0.0.1:5173/projects` 后打开网页。

浏览器访问 `http://127.0.0.1:5173/projects`。

## 从空白开始的 10 步

| 步 | 在哪 | 做什么 | 做完应该看到 |
|---|---|---|---|
| 1 | 项目列表页 | 点「新建项目」，名字填 `一箭又一箭` | 列表里出现 1 个项目 |
| 2 | 项目详情 | 点「上传项目 ZIP」，选 `examples/arrow-game/一箭又一箭_测试需求简版.zip` | 出现候选接口 `POST /game/move`、顶部黄条消失 |
| 3 | 项目资料 | 勾上 `POST /game/move` 确认登记 | 「已登记接口」里 1 条 |
| 4 | 项目资料 | 「选择需求文档」选 `测试需求_请选这个.md` → 起始字符 `0`、结束留空 → 点「预览文档」 | 内容填进下面「需求原文」大文本框 |
| 5 | 需求原文 | 点「保存需求」 | 存成 v1，「检查缺项」按钮变亮 |
| 6 | 需求页 | 点「检查缺项」 | 问出几条**功能大白话**（点空格算不算失误、挡路看多远……） |
| 7 | 需求页 | 把下面「补充约定」整段贴到需求末尾，保存成 v2 | 再点「检查缺项」→「当前范围无需继续追问」 |
| 8 | 测试用例页 | 需求下拉选 **v2** → 「生成候选用例」→ 逐条「编辑候选」→「保存用例」→「确认 v1」 | 出现「前往执行页」 |
| 9 | **环境配置页** | 选「项目本地服务」→ 服务标识 `arrow-game`、回环地址 `http://127.0.0.1:18085` → 勾「该服务不需要登录（不使用凭据）」→ 保存 | 环境版本 `v1`、服务标识 `arrow-game` |
| 10 | 执行页 | 核对目标是 `arrow-game / 18085`、无黄色警告 → 点「执行所选」 | 跳结果页，看 PASS/FAIL 和 HTML 报告 |

三个容易踩的坑：

- 第 4 步「需求原文」上面那个下拉**不是选文档用的**，它列的是已保存的需求版本（新需求 / v1 / v2…），显示 `Select` 是正常的。真正确认包传对了，看「有没有出现候选接口 `POST /game/move`」。
- 第 8 步的需求下拉**默认是 v1**，一定手动切到 v2，否则拿旧需求去生成。
- 第 9 步是硬性前置：不配的话执行页显示「未配置」并出黄条，「执行所选」按钮一直是灰的。这里填的只是「平台去哪台服务上测」，每个新项目配一次就够。

如果页面上残留假的示例用例，那是浏览器本地缓存。按 F12 在控制台贴一行回车即可：

```js
localStorage.removeItem('testpilot-authoring-demo-v1'); location.reload();
```

## 可直接粘贴的补充答案（v2，全是功能大白话）

```
## 补充约定（把功能说清楚）

- 点到空格（没有箭头的格子）不算失误，箭头不动，机会不扣，这一下就当没发生。
- 被挡那一次算一次失误：本来 3 次机会，扣完剩 2 次；畅通消掉那一次不扣，仍是 3 次。
- 判断前面有没有挡路，要顺着箭头方向一直看到棋盘边界，不是只看挨着的一格；中间隔着空格、更远处还有箭头，也算被挡。
- 把棋盘上的箭头全部消掉就算过关，指的是「这一下把最后一支箭消掉」的那一次。
- 本次只验证「一次点击」的规则：点到什么、消不消、扣不扣机会、通没通关。连续点到 3 次机会用完会怎样、过关后要不要进下一关、中途重新开始，这几件流程上的事这次不测。

游戏对外怎么请求、返回里有哪些栏位，项目包自带的《接口说明》已经写好，按那份来，不用另外确认。
```

这段和项目的实际行为一致，生成出来的用例能跑出 PASS。补完再点「检查缺项」会回到「当前范围无需继续追问」。

## 结果页怎么读

`status`（要 200 还是 422）、`json_equals`（某个字段该等于什么）这些断言，**差异写「字段不存在」多半是断言路径写法问题；差异写「期望 blocked，实际 removed」这种值对不上，才是被测项目真的跟需求不一致**。

平台以前有个判定缺陷：断言路径只认对象键，不认数组下标，模型按习惯写 `board.0` 会被误报「字段不存在」。这个已经修好（`backend/app/modules/runs/executor.py` 支持数组下标），现在不会再出现这类假 FAIL。

### 典型的一轮：3 PASS / 2 FAIL，两条都怪用例

真实模型生成的 5 条候选用例里，常有两条写错，游戏两次都按需求正确返回：

| 失败用例 | 报错 | 真实原因 |
|---|---|---|
| 隔一格有箭头也算挡路 | `HTTP 状态：期望 200，实际 422`，后面一串「字段不存在」 | 用例把棋盘写成 `["R..U","...","..."]`，第一行 4 个字符、后两行 3 个，**不是矩形**；游戏按规矩回 `422 A board must be rectangular` |
| 前方无阻挡：箭头消掉并过关 | `state：期望 'playing'，实际 'complete'` | 棋盘只有一支箭，消掉后棋盘空了，按需求应回 `complete`；用例标题写「并过关」，断言却写 `playing`，**自己跟自己打架** |

第一条里那串「字段不存在」是连带现象：422 的响应体只有一句 `detail`，没有 `kind`/`lives`/`state`/`board`，所以后面几条断言全取不到值，根子是那个 422。

**怎么改（正好演示「人工复核」这一环）**：进「测试用例」页 →「已保存的用例」→ 点那条「编辑用例」，**只改下面这两处，其它原样保留**：

- 第 4 条：把 `body.board` 从 `["R..U","...","..."]` 改成 `["R..U","....","...."]`（后两行补齐成 4 列）。
- 第 5 条：把 `assertions` 里 `path` 为 `state` 的那条 `expected` 从 `"playing"` 改成 `"complete"`。

> 不要整段复制别人的步骤 JSON：里面的 `endpoint_id` 是每台电脑导入接口时各自生成的，抄过来会对不上。只改字段最稳妥；确实要整段替换的话，先把原 JSON 里的 `endpoint_id` 抄出来填回去。

改完保存，用例会变成 `v2 · NEEDS_REVIEW`（改过就要重新复核），点「确认 v2」，再回执行页把 5 条重跑一次，就是 5 PASS。

**答辩可以这么讲**：AI 连测试用例都会写错——一条棋盘不合规、一条预期自相矛盾，所以平台才把「人工确认」放在自动生成和执行之间。这一轮不是「测出游戏做偏了」，而是「测出用例写偏了」，两件事都说明自动测试离不开人复核。

## 进阶：想演示「测出 AI 做偏了」

上面第 5 条特意收敛了范围。把「本次只验证一次点击」那句**换成**：

```
我本来想要能一直玩下去：连续被挡 3 次就算这一关失败，过关后自动进下一关，中途还能重新开始。
```

平台拿这句去生成用例，就会去测「连点几次、机会会不会递减」「有没有下一关」。可这个项目每次请求都是全新一关、只点一下，压根没有这些流程，用例会 FAIL。**这才是测试平台最该展示的价值：把 AI 偷偷做偏的地方测出来**，答辩时讲这一句比全 PASS 更有说服力。

## 名词对照（给没接触过的同学）

| 词 | 大白话 |
|---|---|
| 端口 | 一台电脑上服务的「房间号」，`18085` 是小游戏，`8000` 是平台后台，`5173` 是网页 |
| 接口 | 「用什么方式、去哪个窗口办哪件事」，`POST /game/move` 就是带棋盘数据去让小游戏算一步 |
| 环境配置 | 告诉平台「去哪台服务上测」，这里填 `http://127.0.0.1:18085` |
| 用例 | 一张检查单：发什么请求、期望返回什么 |
| PASS / FAIL | 检查结果和预期对得上 / 对不上 |
