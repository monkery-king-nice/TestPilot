操作员亲自执行的批次为 `d39ad12a-a544-4ad7-9d36-b3a2219ac81d`，用例为 `f8a6cab4-4755-433c-9978-8b87256aa13f` v1。原报告 SHA-256 为 `1d52ada8a5178e3b64b318f128baae67be88fc8616fc7a878b1ef15961d103a6`。

DeepSeek 引用了「me · HTTP 200 · 阶段 assertion · user.id：期望 'qa-expected-user'，实际 'demo-user'」。它将账号身份和用例预期配置列为待检查项，并说明现有证据不足以确定根因。在本次演示中，团队知道预期值是人为设置的。

前几次尝试收到上游 HTTP 401。使用本机密码输入框重新输入后，复核程序在后台调用了分析接口并保存结果。此次真实模型验收覆盖分析接口，分析正文由复核程序收集。

## 复核方法

1. 从执行详情网址记录项目与批次 ID，从该批次结果记录 case_id。保存分析前的详情与 HTML 报告。
2. 在同一批次点击「AI 失败分析」，或向 `/api/projects/{project_id}/runs/{run_id}/analysis` POST `{"case_id":"实际用例ID"}`。保留模型名、返回的分类、解释、引用与建议。核对 HTTP 成功与字段断言失败两项事实。
3. 再读取同一批次的详情和报告，与调用前的结果、计数和 HTML 内容逐项或逐字节比较。在独立禁用模型实例重复读取，记录分析响应与报告是否可用。
4. 使用仓库根目录的 `python -m pytest -q` 运行回归。自动测试覆盖 FAIL 引用空列表、仅成功步骤、越界以及有效引用。真实模型结论以现场记录为准。
